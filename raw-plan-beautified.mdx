# FlowKit: Ready-to-Build MVP Implementation Plan

## Executive recommendation

<Aside type="tip" title="Executive recommendation">
FlowKit should be implemented as a small Python CLI that runs one sequential tabular machine-learning workflow, launches Codex or OpenCode in the project directory, validates structured session results, and persists workflow state in YAML and Markdown files.

The first vertical slice should support one binary-classification project using a local CSV dataset.

The recommended MVP workflow is:

<Steps>
1. Understand problem
2. Assess data
3. Build baseline
4. Improve model
5. Review results
6. Finalize solution
</Steps>

This intentionally combines:

- Inspect data + Validate data into **Assess data**
- Create baseline + Analyze baseline into **Build baseline**
- Engineer features + Run experiments into **Improve model**

FlowKit should automatically advance after a stage completes successfully unless a human gate is required. A separate `next` command is unnecessary in the MVP.

`Experiment` should be a core FlowKit concept, but only as a small, readable record. Dataset, metric, feature, and model should remain fields inside project configuration and experiment records rather than becoming separate domain objects.
</Aside>

---

# 1. Implementation summary

FlowKit manages the execution record around a tabular ML project.

A team member initializes FlowKit inside an existing project:

```bash
cd churn-project
flowkit init
```

They configure:

```yaml
task_type: binary_classification
dataset_path: data/train.csv
target_column: churn
primary_metric: roc_auc
```

They then start and run the workflow:

```bash
flowkit start
flowkit status
flowkit run
```

For each stage, FlowKit:

<Steps>
1. Loads the workflow definition.
2. Loads project configuration and accumulated context.
3. Creates an agent session directory.
4. Builds a stage-specific prompt.
5. Starts Codex or OpenCode in the project directory.
6. Streams the interactive agent session to the terminal.
7. Captures the session transcript and exit code.
8. Reads a structured `result.yaml` produced by the agent.
9. Validates required source files, artifacts, and experiment records.
10. Updates `state.yaml`, `context.md`, and `experiments.yaml`.
11. Moves to the next stage or waits for human approval.
</Steps>

# 2. Critical roadmap review

## 2.1 Stage list is too granular for the first implementation

The proposed workflow has nine or ten stages. Several stages naturally share the same context, agent session, and artifacts.

For example:

```text
Inspect data
Validate data
Identify leakage
```

will normally happen in the same analysis session.

Similarly:

```text
Create baseline
Analyze baseline
Evaluate baseline
```

will usually use the same training code and report.

### Recommendation

Use six MVP stages:

```text
1. understand_problem
2. assess_data
3. build_baseline
4. improve_model
5. review_results
6. finalize_solution
```

The workflow format should still allow more stages later, but the built-in workflow should remain small.

---

## 2.2 Stage completion cannot depend on prose output

An agent may claim that work is finished without creating the expected files or recording a metric.

### Recommendation

Every agent session must produce:

```text
.flowkit/sessions/<session-id>/result.yaml
```

FlowKit should never determine completion by parsing the terminal transcript.

The result file contains:

```yaml
outcome: completed
summary: Baseline logistic regression trained and evaluated.
artifacts:
  - .flowkit/artifacts/baseline-report.md
project_files:
  - src/train.py
experiments:
  - local_ref: baseline-logistic
question: null
```

FlowKit validates this result against actual files and workflow requirements.

---

## 2.3 Project configuration location is unclear

Dataset path, target, metric, task type, and validation strategy are not workflow-engine settings. However, introducing another file immediately adds storage complexity.

### Recommendation

For the MVP, store these settings under a `project` section in `flow.yaml`.

```yaml
project:
  task_type: binary_classification
  dataset_path: data/train.csv
  target_column: churn
  primary_metric:
    name: roc_auc
    direction: maximize
```

Move them into `project.yaml` only when multiple workflows need to share the same project configuration.

---

## 2.4 Experiment recording needs a canonical owner

Allowing agents to directly append to `experiments.yaml` risks malformed YAML, duplicate IDs, and partially written records.

### Recommendation

The agent proposes experiments in its session `result.yaml`.

FlowKit:

1. Validates the proposed experiment.
2. Assigns the canonical experiment ID.
3. Appends it to `experiments.yaml`.
4. Updates the latest and best experiment fields in `state.yaml`.

The agent should not directly update canonical state files.

---

## 2.5 Metrics need comparison direction

A metric name alone is insufficient.

Higher values are better for ROC-AUC, F1, and recall. Lower values are better for RMSE, MAE, and log loss.

### Recommendation

Represent the primary metric as:

```yaml
primary_metric:
  name: roc_auc
  direction: maximize
```

Store all metrics as numeric values. FlowKit only compares the configured primary metric.

---

## 2.6 Validation strategy needs to be explicit

Experiments are not comparable if different splits or validation procedures are silently used.

### Recommendation

Make validation strategy part of project configuration and repeat it in every experiment record.

Initial supported strategies:

```text
holdout
kfold
stratified_kfold
```

The first vertical slice should implement only:

```yaml
validation:
  type: holdout
  test_size: 0.2
  stratify: true
  random_seed: 42
```

FlowKit records other values but does not execute the split itself.

---

## 2.7 Agent file modifications cannot be fully enforced

A prompt can tell an agent which files it may modify, but it cannot guarantee compliance.

### Recommendation

Before and after every session, FlowKit records:

```bash
git status --porcelain
git diff --name-only
```

If Git is unavailable, FlowKit falls back to file timestamps for declared paths.

Unexpected changed paths should cause validation to fail or require human approval.

FlowKit should warn rather than attempt to build a full sandbox.

---

## 2.8 Resume behavior differs between agents

Codex and OpenCode may have different session-resume capabilities, and their CLI behavior may change.

### Recommendation

Do not depend on native agent resume for correctness.

Each new session receives:

* Current stage instructions
* `context.md`
* Relevant decisions
* Selected artifacts
* Recent experiment summaries
* Previous session summary

Native resume may be used as an optimization, but starting a new session must always work.

---

## 2.9 Core-concept decision

| Candidate     | MVP decision                         | Reason                                              |
| ------------- | ------------------------------------ | --------------------------------------------------- |
| Workflow      | Core object                          | Defines ordered stages and rules                    |
| Run           | Core object                          | Represents one execution of a workflow              |
| Stage         | Core object                          | Primary execution and transition unit               |
| Skill         | Simple stage field                   | A path or instruction reference is enough           |
| Artifact      | Core object, lightweight             | Required for completion validation                  |
| Gate          | Core object, lightweight             | Needed for meaningful human decisions               |
| Agent Session | Core object                          | Needed for lifecycle, transcript, and handoff       |
| Experiment    | Core object, lightweight             | Required for repeated model attempts and comparison |
| Metric        | Structured field                     | Does not need independent lifecycle                 |
| Dataset       | Project configuration field          | One main dataset is sufficient for MVP              |
| Model         | Experiment field                     | Avoid building a model registry                     |
| Feature       | Artifact content or experiment field | Avoid a feature-store abstraction                   |

---

## 2.10 Work to postpone

Postpone:

* Forecasting-specific stages
* Anomaly-detection-specific stages
* Multiple datasets per run
* Dataset fingerprinting beyond a simple hash
* Agent plugin registration
* Dynamic stage graphs
* Parallel experiments
* Experiment dashboards
* Automatic dependency installation
* Automatic Git commits
* Automatic hyperparameter optimization
* Full agent sandboxing

# 4. Final MVP CLI

The recommended command set is:

```text
flowkit init
flowkit start
flowkit status
flowkit run
flowkit gate approve
flowkit gate reject
flowkit retry
flowkit back
flowkit stop
flowkit resume
```

There is no `next` command. Successful validation automatically advances the workflow.

## 4.1 `flowkit init`

### Syntax

```bash
flowkit init [--workflow tabular] [--force]
```

### Purpose

Create the `.flowkit/` directory and default tabular workflow.

### Arguments

None.

### Options

```text
--workflow tabular   Workflow template. Only tabular exists in MVP.
--force              Replace existing unstarted FlowKit configuration.
```

### State changes

Creates initial files with run status `not_started`.

### Common errors

* `.flowkit/` already exists
* Project directory is not writable
* Existing state contains an active run
* Unsupported workflow template

### Example

```bash
flowkit init
```

---

## 4.2 `flowkit start`

### Syntax

```bash
flowkit start [--run-id ID]
```

### Purpose

Validate configuration and create a new workflow run.

### Options

```text
--run-id ID   Optional manually chosen run ID.
```

### State changes

* Creates run ID
* Sets run status to `active`
* Sets first stage to `pending`
* Adds transition-history entry

### Validation

* Dataset path exists
* Target column is configured
* Primary metric contains name and direction
* Workflow contains at least one stage
* Stage IDs are unique
* Referenced instruction files exist

### Common errors

* Run already active
* Dataset missing
* Invalid YAML
* Duplicate stage IDs
* Unsupported task type

---

## 4.3 `flowkit status`

### Syntax

```bash
flowkit status [--verbose] [--json]
```

### Purpose

Display the current run, stage, session, gate, artifact, and experiment state.

### Options

```text
--verbose   Include completed stages and recent history.
--json      Emit machine-readable JSON.
```

### State changes

None.

### Output should always answer

* Which workflow is running?
* Which stage is current?
* What is the stage status?
* Which session is active?
* Which artifacts are expected?
* Is a human gate pending?
* What is the latest experiment?
* What is the best primary metric?
* What command should be run next?

### Common errors

* FlowKit not initialized
* Invalid state file
* Referenced workflow missing

---

## 4.4 `flowkit run`

### Syntax

```bash
flowkit run \
  [--agent codex|opencode] \
  [--new-session] \
  [--repeat-exp EXPERIMENT_ID]
```

### Purpose

Run the current stage using an AI agent.

### Options

```text
--agent           Override the preferred stage agent.
--new-session     Force a fresh session.
--repeat-exp      Ask the agent to repeat or modify a prior experiment.
```

### State changes

Before launch:

* Stage status becomes `running`
* New session record is created
* Active session is stored
* Start transition is recorded

After launch:

* Session exit code and summary are stored
* Artifacts and experiments are validated
* Stage becomes `completed`, `failed`, or `waiting_for_human`
* Run advances automatically when allowed

### Common errors

* Stage already running
* Run stopped
* Human gate pending
* Agent command unavailable
* Retry limit reached
* Invalid previous experiment ID
* Required project files missing

---

## 4.5 `flowkit gate approve`

### Syntax

```bash
flowkit gate approve [--answer TEXT] [--reason TEXT]
```

### Purpose

Approve a pending human gate and optionally provide a selected answer.

### State changes

* Gate status becomes `approved`
* Decision is appended to `decisions.md`
* Context is updated
* Stage completes if no other requirement is pending
* Workflow advances automatically

### Common errors

* No pending gate
* Required answer missing
* Answer not one of the allowed options
* Gate already resolved

---

## 4.6 `flowkit gate reject`

### Syntax

```bash
flowkit gate reject --reason TEXT [--answer TEXT]
```

### Purpose

Reject the recommendation or completion proposal.

### State changes

* Gate resolution is recorded as rejected
* Current stage becomes `failed`
* Retry becomes available
* Rejection reason enters the next session context

### Common errors

* No pending gate
* Missing rejection reason
* Gate already resolved

---

## 4.7 `flowkit retry`

### Syntax

```bash
flowkit retry [--agent codex|opencode]
```

### Purpose

Create a new attempt for the failed or rejected current stage.

### State changes

* Retry counter increases
* Previous session and artifacts remain
* New session is created
* Stage returns to `running`
* Failure history remains immutable

### Common errors

* Current stage is not failed
* Retry limit reached
* Another session is still alive

---

## 4.8 `flowkit back`

### Syntax

```bash
flowkit back [--to STAGE_ID] --reason TEXT
```

### Purpose

Return to a previous stage.

### State changes

* Selected previous stage becomes current and `pending`
* Later stages become `pending`
* Existing artifacts and experiments are preserved
* History records that later results may no longer be current
* Best experiment is recalculated from non-invalidated experiments

### Common errors

* No previous stage
* Current stage is running
* Pending human gate exists
* Unknown target stage

---

## 4.9 `flowkit stop`

### Syntax

```bash
flowkit stop [--reason TEXT]
```

### Purpose

Pause the current run without deleting state.

### State changes

* Run status becomes `stopped`
* Running stage becomes `stopped`
* Active agent receives an interrupt
* Session is finalized as interrupted

### Common errors

* Run is already stopped
* No active run

---

## 4.10 `flowkit resume`

### Syntax

```bash
flowkit resume
```

### Purpose

Resume a stopped run.

### State changes

* Run status becomes `active`
* Stopped stage becomes `pending`
* Previous session remains closed
* Next `flowkit run` creates a new session

### Common errors

* Run is not stopped
* State validation fails
* Dataset or configuration is no longer available

---

# 5. Minimal domain model

## 5.1 Workflow

### Responsibility

Defines ordered stages, stage requirements, and ML project configuration.

### Minimum fields

```yaml
id: tabular-model-development
name: Tabular Model Development
version: 1
stages: [...]
```

### Storage

`.flowkit/flow.yaml`

### Relationships

Contains stage definitions. Used by one or more runs.

### Example

The built-in churn-model-development workflow.

---

## 5.2 Run

### Responsibility

Represents one execution of a workflow.

### Minimum fields

```yaml
id: run-20260711-001
workflow_id: tabular-model-development
status: active
current_stage: build_baseline
started_at: 2026-07-11T11:30:00+07:00
stopped_at: null
```

### Storage

`.flowkit/state.yaml`

### Relationships

Has stage runtime states, sessions, gates, artifacts, and experiments.

---

## 5.3 Stage

### Responsibility

Represents one meaningful unit of sequential work.

### Definition fields

```yaml
id
name
instruction
preferred_agent
session_policy
expected_artifacts
required_project_files
completion
gate
retry
next
```

### Runtime fields

```yaml
status
attempt
started_at
completed_at
session_ids
last_error
```

### Example

`build_baseline`

---

## 5.4 Artifact

### Responsibility

Represents a required human-readable or machine-readable output.

### Minimum fields

```yaml
id: baseline-report
path: .flowkit/artifacts/baseline-report.md
type: markdown
stage: build_baseline
required: true
produced_by: session-003
checksum: optional
```

### Storage

Artifact metadata is stored in `state.yaml`. Artifact contents are stored at their declared paths.

### Example

A Markdown report explaining baseline preprocessing, metrics, and weaknesses.

---

## 5.5 Gate

### Responsibility

Blocks progression until a meaningful human decision is recorded.

### Minimum fields

```yaml
id
stage
status
question
options
recommendation
answer
reason
requested_by_session
resolved_at
```

### Storage

Current gate in `state.yaml`. Final decision in `decisions.md`.

---

## 5.6 Agent Session

### Responsibility

Records one invocation of Codex or OpenCode.

### Minimum fields

```yaml
id

status

```

### Storage

Session metadata in:


Current session reference in `state.yaml`.

## 5.7 Experiment

### Responsibility

Records one reproducible model-training and evaluation attempt.

### Minimum fields

```yaml
id
timestamp
stage
session_id
command
dataset
feature_set
model_type
parameters
validation
metrics
status
artifact_paths
notes
```

### Storage

`.flowkit/experiments.yaml`

### Why it is a core concept

FlowKit must answer:

* What was the last experiment?
* What was the best experiment?
* Which validation strategy was used?
* Which model and parameters produced a metric?
* Which session created the result?

Artifacts alone cannot reliably answer these questions.

Experiment should therefore be a core object, but it must remain a simple record rather than becoming an execution engine.

---

## Non-core ML concepts

### Dataset

Store as project configuration and repeat its path or fingerprint in experiment records.

Do not create a dataset registry.

### Metric

Store as structured project configuration and numeric experiment fields.

Do not create independent metric objects.

### Feature

Record feature-set descriptions or references such as:

```yaml
feature_set:
  id: feature-set-v2
  source: src/features.py
  description: Tenure buckets and contract interaction features.
```

Do not create a feature store.

### Model

Store model type and artifact path in the experiment.

Do not create a model registry.

## Safe state updates

Every command that mutates state should:

1. Acquire `.flowkit/state.lock`.
2. Reload `state.yaml` after acquiring the lock.
3. Validate schema and current transition.
4. Modify state in memory.
5. Serialize to `.flowkit/state.yaml.tmp`.
6. Flush and call `fsync`.
7. Copy the previous valid state to `state.yaml.bak`.
8. Atomically replace the original with `os.replace`.
9. Release the lock.

Session execution should not hold the state lock for the entire agent process.

Instead:

* Store the agent PID and session ID before launch.
* Release the lock.
* Launch the process.
* Reacquire the lock for completion updates.

A command should reject starting another session when the stored PID is alive.

# 10. Stage lifecycle

## Stage statuses

```text
pending
running
waiting_for_human
completed
failed
stopped
```

## Run statuses

```text
not_started
active
waiting_for_human
stopped
completed
failed
```

## Valid stage transitions

```text
pending → running
running → completed
running → waiting_for_human
running → failed
running → stopped
waiting_for_human → completed
waiting_for_human → failed
failed → running
stopped → pending
completed → pending   # only through back
```

## Invalid transitions

```text
pending → completed
pending → waiting_for_human
completed → running without back
waiting_for_human → running before gate resolution
failed → completed without a new attempt
running → running
```

## Completion validation

For `build_baseline`, completion requires:

```text
Agent exit code is zero
result.yaml exists and is valid
result outcome is completed
src/train.py exists
baseline-report.md exists and is non-empty
At least one experiment proposal exists
Primary metric exists and is numeric
Validation strategy matches project configuration
Experiment command is present
No duplicate experiment ID or local reference exists
No disallowed project-file changes are detected
```

## Preventing concurrent execution

Before starting an agent:

1. Check `active_session`.
2. Check whether its PID is alive.
3. Check stage status.
4. Acquire a short-lived mutation lock.
5. Register the new session and PID.

Only one active session is supported per project.

## Preventing duplicate experiment IDs

FlowKit assigns canonical IDs using:

```text
exp-YYYYMMDD-NNN
```

The next sequence is calculated while holding the state lock.

Agent-provided IDs are treated only as local references.

## Preventing premature advancement

FlowKit advances only through one function:

```python
complete_current_stage()
```

That function always runs the configured completion validators.

There should be no generic `set_current_stage()` CLI action.

## Preventing unrecorded retries

A failed attempt remains in:

* Stage `session_ids`
* Session directory
* Transition history
* Retry count
* `last_error`

A retry always creates a new session.

# 11. Human gate behavior

## Recommended gates

Use human gates for:

1. Problem definition and metric approval
2. Major validation-strategy change
3. Expensive or unusually large experiment plan
4. Final experiment selection
5. Final solution approval

Do not require approval after routine data inspection or every experiment.

## Agent request contract

When the agent needs a decision:

```yaml
outcome: needs_human

question:
  id: metric-priority
  text: >
    Should model comparison optimize ROC-AUC or churn-class recall?
  options:
    - roc_auc
    - recall
  recommendation: roc_auc
  reason: >
    ROC-AUC is threshold-independent and better suited to initial model
    comparison.
  blocking: true
```

## FlowKit behavior

FlowKit:

1. Validates the question structure.
2. Sets stage to `waiting_for_human`.
3. Sets run to `waiting_for_human`.
4. Stores the pending gate in `state.yaml`.
5. Prints the question and recommendation.
6. Waits for `flowkit gate approve` or `flowkit gate reject`.

## Approval example

```bash
flowkit gate approve \
  --answer roc_auc \
  --reason "Use recall as a secondary operational metric"
```

FlowKit appends the decision to `decisions.md` and updates `context.md`.

## Session continuation

Default policy:

* Close the session that asked the question.
* After approval, either complete the stage or start a new session.

Do not assume the original agent process can resume.

For questions raised before work is complete, the next `flowkit run` starts a fresh session containing the answer.

For gates raised after all stage work is complete, approval completes the stage without starting another session.

# 12. Agent execution

## Invocation strategy

Use Python `subprocess` with a pseudo-terminal so the user can interact with the agent.

Initial executable names:

```text
codex
opencode
```

Do not depend on unstable prompt flags.

MVP invocation approach:

1. Start the configured executable in the project root.
2. Open an interactive PTY.
3. Send the generated prompt through stdin.
4. Stream combined terminal output to the user.
5. Save the raw stream to `transcript.log`.
6. Wait for the process to exit.
7. Validate `result.yaml`.

This supports CLI changes better than building around agent-specific flags.

## Minimal adapter interface

```python
class AgentRunner:
    def is_available(self) -> bool: ...
    def start(
        self,
        command: list[str],
        cwd: Path,
        prompt: str,
        transcript_path: Path,
    ) -> AgentProcessResult: ...
```

Codex and OpenCode need small command-building functions, not a plugin framework.

## Prompt construction

The final prompt should contain these sections:

```text
1. FlowKit stage
2. Stage objective
3. Project ML configuration
4. Accepted decisions
5. Relevant data findings
6. Recent and best experiment results
7. Previous session summary
8. Files the agent may modify
9. Files the agent must not modify
10. Required project files
11. Required artifacts
12. Experiment record schema
13. Human-question schema
14. Completion instructions
```

## Example prompt ending

```text
Before exiting, write:

.flowkit/sessions/session-003/result.yaml

Use exactly one of these outcomes:

- completed
- needs_human
- failed

Do not claim completion unless all required files exist.

For every training attempt, include an experiment proposal with:
- command
- model type
- parameters
- validation strategy
- metrics
- output paths

If a major decision is required, stop and use outcome: needs_human.

Do not directly edit:
- .flowkit/state.yaml
- .flowkit/experiments.yaml
- .flowkit/decisions.md
- .flowkit/context.md
```

## Exit handling

### Exit code 0

Validate result and files. Exit code zero alone does not complete the stage.

### Non-zero exit

Mark the attempt failed unless a valid result explicitly describes an intentional human stop.

### Missing result file

Mark the attempt failed:

```text
Agent exited without writing the required session result.
```

### Interrupted process

Mark the session `interrupted` and stage `stopped` or `failed`, depending on whether the user used `flowkit stop`.

## Session IDs

Use monotonic IDs:

```text
session-001
session-002
session-003
```

IDs only need to be unique inside one project.

## Resume behavior

Native agent resume is optional.

If native resume metadata is available, store it in `session.yaml`:

```yaml
native_resume:
  supported: true
  reference: agent-specific-reference
```

A new session remains the default after interruption or gate resolution.

# 13. Retry, back, stop, and resume

## Retry

Meaning:

> Repeat the current failed or rejected stage as a new attempt.

Preserved:

* Previous artifacts
* Previous sessions
* Previous experiment records
* Context and decisions
* Error history

Changed:

* Retry counter increases
* New session is created
* Stage becomes running

Limit:

* Default 3 attempts
* Improve-model stage may allow 5 attempts

Previous failed experiments remain recorded with `status: failed` only if enough metadata exists to create a meaningful record.

---

## Back

Meaning:

> Return to a previous stage because an earlier assumption or decision must be revised.

Preserved:

* All artifacts
* All sessions
* All experiments
* Full history

Changed:

* Target stage becomes `pending`
* Later stages become `pending`
* Later experiments are marked:

```yaml
validity: needs_review
```

* Selected experiment is cleared when affected
* Best experiment is recalculated from still-valid records

A reason is required.

---

## New session

Meaning:

> Execute the same current stage using fresh agent context.

A new session does not automatically increase retry count unless the previous session failed.

Use:

```bash
flowkit run --new-session
```

This is useful when an agent session becomes too long or confused.

---

## Repeat experiment

Meaning:

> Ask the current-stage agent to rerun or modify an existing experiment.

Use:

```bash
flowkit run --repeat-exp exp-20260711-001
```

The previous experiment remains unchanged.

The repeated run receives a new experiment ID.

The new record may include:

```yaml
parent_experiment_id: exp-20260711-001
```

---

## Stop

Meaning:

> Pause the run safely.

FlowKit sends an interrupt to an active agent, closes the transcript, saves the interruption, and sets the run to stopped.

No artifact or context is deleted.

---

## Resume

Meaning:

> Make a stopped run active again.

Resume does not reopen the old agent process.

The next `flowkit run` creates a new session with the stopped session summary.

---

## Failure handling

| Failure                    | FlowKit response                                              |
| -------------------------- | ------------------------------------------------------------- |
| Dataset file not found     | Reject `start` or fail pre-run validation                     |
| Target column missing      | Reject `start` after reading the dataset header               |
| Agent command not found    | Fail before session launch                                    |
| Python script fails        | Agent records failure; stage becomes failed                   |
| Dependency missing         | Preserve traceback and recommend environment fix              |
| Non-zero agent exit        | Stage fails unless explicitly stopped                         |
| Interrupted terminal       | Finalize transcript; detect orphan process on next command    |
| Required artifact missing  | Stage validation fails                                        |
| Invalid metric value       | Reject NaN, infinity, strings, or missing primary metric      |
| Incomplete experiment      | Reject experiment ingestion and fail stage validation         |
| Invalid state file         | Load backup and report recovery; never overwrite immediately  |
| Stage already running      | Reject second run command                                     |
| Gate not approved          | Block new run and advancement                                 |
| Summary generation failure | Preserve transcript; create fallback summary from result file |
| Invalid result YAML        | Fail session validation and preserve the invalid file         |
| Unexpected changed files   | Block completion or require approval                          |
| State lock unavailable     | Report another FlowKit command is mutating state              |

## Update best experiment

```python
def update_best_experiment(state, experiments, project):
    comparable = [
        exp for exp in experiments
        if experiment_is_comparable(exp, project)
    ]

    if not comparable:
        clear_best_experiment(state)
        return

    metric_name = project.primary_metric.name
    direction = project.primary_metric.direction

    key = lambda exp: exp.metrics[metric_name]

    if direction == "maximize":
        best = max(comparable, key=key)
    else:
        best = min(comparable, key=key)

    state.experiments.best_id = best.id
    state.experiments.best_primary_metric.value = best.metrics[metric_name]
```

```python
def back_to_stage(root, target_stage_id, reason):
    with state_lock(root):
        flow, state = load_project(root)

        require_no_live_session(state)
        require_no_pending_gate(state)

        target_index = flow.stage_index(target_stage_id)
        current_index = flow.stage_index(state.run.current_stage)

        require(target_index < current_index)

        for stage in flow.stages[target_index:]:
            state.stages[stage.id].status = "pending"

        invalidate_dependent_experiments(
            root,
            from_stage_index=target_index,
        )

        state.selected_experiment = None
        state.run.current_stage = target_stage_id
        append_back_decision(root, target_stage_id, reason)
        append_history(state, "workflow_back", stage=target_stage_id)

        save_state_atomically(root, state)
```

## Stop and resume

```python
def stop_run(root, reason):
    state = load_state(root)

    if state.active_session:
        interrupt_process(state.active_session.pid)
        finalize_interrupted_session(state.active_session)

    with state_lock(root):
        state = load_state(root)
        state.run.status = "stopped"
        state.stages[state.run.current_stage].status = "stopped"
        state.active_session = None
        append_history(state, "run_stopped", reason=reason)
        save_state_atomically(root, state)


def resume_run(root):
    with state_lock(root):
        state = load_state(root)
        require(state.run.status == "stopped")

        state.run.status = "active"
        state.stages[state.run.current_stage].status = "pending"
        append_history(state, "run_resumed")
        save_state_atomically(root, state)
```

## Save state atomically

```python
def save_state_atomically(root, state):
    path = root / ".flowkit/state.yaml"
    tmp = root / ".flowkit/state.yaml.tmp"
    backup = root / ".flowkit/state.yaml.bak"

    serialized = dump_yaml(state)

    write_bytes(tmp, serialized)
    fsync_file(tmp)

    if path.exists():
        copy_file(path, backup)
        fsync_file(backup)

    os.replace(tmp, path)
    fsync_directory(path.parent)
```

# 19. Decisions, risks, and postponed work

## Decisions to lock now

### Supported task

The first completed vertical slice supports:

```text
binary classification
```

The schemas should allow regression, but regression does not need full end-to-end acceptance until after the churn workflow works.

### Dataset format

Initial support:

```text
One local CSV file
One required target column
```

Parquet and multiple datasets are postponed.

### Primary metric

Required structure:

```yaml
primary_metric:
  name: roc_auc
  direction: maximize
```

### Validation strategy

First working strategy:

```yaml
type: holdout
test_size: 0.2
stratify: true
random_seed: 42
```

FlowKit records and compares configuration but does not implement the split.

### Experiment storage

Use one canonical `.flowkit/experiments.yaml`.

Agents propose records through session `result.yaml`; FlowKit assigns IDs and persists them.

### Stage completion

Completion requires:

* Successful agent exit
* Valid structured result
* Required artifacts
* Required project files
* Required experiment and metric data
* No blocking human question
* No disallowed modifications

### Session policy

Default to a new session for every stage and every retry.

Never depend completely on agent resume.

### Agent invocation

Run `codex` or `opencode` as local interactive PTY subprocesses in the project root.

Pass the generated prompt through stdin.

### State ownership

Only FlowKit writes:

```text
state.yaml
experiments.yaml
decisions.md
context.md
```

Agents write artifacts, project files, and session results.

## Main risks

### Agent output is inconsistent

Mitigation:

* Strict `result.yaml` schema
* Artifact validation
* Clear prompt contract
* Fail closed when required data is absent

### Experiment metadata is incomplete

Mitigation:

* Required experiment fields
* Canonical validation before ingestion
* Primary metric mandatory
* Validation configuration mandatory

### Dataset context becomes too large

Mitigation:

* Pass summaries, not full data
* Inspect only metadata and sampled rows
* Keep evidence in artifacts
* Limit `context.md`

### Metrics are not comparable

Mitigation:

* Store dataset path
* Store validation configuration
* Store random seed
* Warn on mismatches
* Only compare valid experiments

### Agents modify unrelated files

Mitigation:

* Allowed-path instructions
* Git diff before and after session
* Block completion on unexpected changes
* Require human review when necessary

### State and project files diverge

Mitigation:

* Validate actual files before transitions
* Use checksums where useful
* Never trust session declarations alone
* Revalidate current stage on resume

### Resume differs between agents

Mitigation:

* New-session fallback
* Persist prompts, summaries, decisions, and experiment history
* Treat native resume as optional metadata

### YAML is corrupted manually

Mitigation:

* Validate on every command
* Maintain `.bak`
* Never overwrite an invalid file automatically
* Provide clear schema errors

### Baseline workflow becomes too opinionated

Mitigation:

* Keep stage instructions editable Markdown
* Keep workflow sequential but configurable
* Avoid hardcoding model libraries

# Final assessment

## Is the roadmap ready for implementation?

Yes.

The roadmap is ready once the decisions in the “Decisions to lock now” section are accepted. No additional large architecture session is required.

The implementation should begin with the file schemas and deterministic lifecycle before real-agent integration.

## ML-specific decisions that still need to be made

The following project-level choices will vary per ML project and should remain configurable:

1. Dataset path
2. Target column
3. Task type
4. Primary metric and comparison direction
5. Secondary metrics
6. Validation strategy
7. Random seed
8. Leakage exclusions
9. Whether model artifacts are required for every experiment
10. Threshold-selection policy for classification

For the first churn vertical slice, lock these defaults:

```yaml
task_type: binary_classification
dataset_path: data/train.csv
target_column: churn

primary_metric:
  name: roc_auc
  direction: maximize

secondary_metrics:
  - f1
  - recall

validation:
  type: holdout
  test_size: 0.2
  stratify: true
  random_seed: 42
```

## Should `Experiment` be a core FlowKit concept?

Yes.

It should be a small core object because FlowKit must reliably track repeated training attempts, comparable metrics, validation settings, model types, and the current best result.

It should not execute training, manage distributed jobs, provide dashboards, or replace MLflow.
